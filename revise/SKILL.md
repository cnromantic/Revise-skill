# Revise

显示名称：Revise  
版本：3.0  
作者：qztcwrh

Revise 用于本科毕业论文（设计）的智能评审、保守修订、PDF 就近批注和结构化修改说明生成。本版本由 ThesisReviewSkill v1.4 演进而来，并固定以下默认策略：**不主动检查 DOI 或参考文献真实性，除非用户明确要求联网核验。**

## 一、默认行为

当用户要求“处理论文”“审阅论文”“修改论文”“处理当前文件夹”“处理 Word/PDF 论文”时，默认执行完整流程：

1. 自动识别输入文件和格式。
2. 同一论文同时存在 Word 和 PDF 时，默认优先处理 Word；用户明确指定 PDF 时处理 PDF。
3. 按本科毕业论文（设计）抽检评议要素进行初评打分。
4. 检查题目、摘要、关键词、英文题名、Abstract、Key words、目录、章节、正文、图表、测试、参考文献。
5. 检查参考文献列表的顺序是否与正文中的引用顺序一致。
6. 软件工程类系统论文额外检查需求分析、系统设计、数据库、接口、实现、测试、截图和技术路线一致性。
7. 能直接修改的低风险问题应生成修改稿，并用黄色突出显示。
8. 不能可靠直接修改的问题，应在修改稿中批注或在修改说明中列明。
9. 生成 Markdown 和 PDF 两种格式的修改说明。
10. 明确列出仍需人工确认的问题。
11. 不伪造实验数据、测试结果、截图、系统功能、源码行为或参考文献信息。

只有在以下情况才询问用户：

- 当前目录下有多篇候选论文，且无法判断处理哪一篇；
- 文件损坏、加密或无法读取；
- 用户要求与默认完整流程冲突；
- 需要联网核验参考文献或 DOI，但用户没有明确授权。

## 二、参考文献默认策略

默认只做以下检查：

- 正文引用序号是否连续；
- 正文引用是否与参考文献列表对应；
- 参考文献格式是否基本符合 GB/T 7714 风格；
- 作者、题名、期刊/出版社、年份、卷期、页码、DOI 等字段是否缺失；
- 文献主题是否与论文主题相关；
- 是否存在明显内部不一致或疑似模板残留。

默认不做以下操作：

- 不联网搜索 DOI；
- 不查询 Crossref、CNKI、万方、出版社、期刊官网或搜索引擎；
- 不声称 DOI、卷期、页码、出版信息已经真实核验；
- 不补造缺失的 DOI、页码、卷期或出版信息。

如未执行联网核验，应在修改说明中写明：**“参考文献真实性及 DOI 需人工或联网核验。”**

只有当用户明确说“请核验 DOI”“请联网检查参考文献”“请验证真实性”等，才执行联网核验。

## 三、处理流程

### 1. 读取论文

提取并识别：

- 论文题目、作者或学号、专业、论文类型；
- 中文摘要、关键词、英文题名、Abstract、Key words；
- 目录与章节标题；
- 图题、表题、图表编号和正文引用；
- 参考文献列表和正文引用序号；
- 软件工程论文中的需求、设计、数据库、实现、测试、接口和截图说明。

按需读取下列参考文件：

- [rubric.md](references/rubric.md)：评分标准；
- [software-engineering-checklist.md](references/software-engineering-checklist.md)：软件工程论文专项检查；
- [style-rules.md](references/style-rules.md)：语言、标点和中英文混排规则；
- [docx-workflow.md](references/docx-workflow.md)：Word 论文处理规则；
- [pdf-workflow.md](references/pdf-workflow.md)：PDF 论文处理规则；
- [report-template.md](references/report-template.md)：修改说明模板。

### 2. 初评打分

先检查否决性指标：

- 政治方向、法律法规、社会公序良俗；
- 明确可见的学术不端证据。

没有确凿证据时，不得直接断定学术不端；只能标为“需人工进一步核查”。

评分必须逐项给出依据，不得只给总分。

### 3. 诊断问题

优先处理高影响问题：

1. 题目、摘要、关键词、系统名称前后不一致；
2. 目录和正文标题不一致，章节缺失、重复、跳号；
3. 图表编号跳号、重复，正文引用与图表题不对应；
4. 需求、设计、数据库、实现、测试和截图之间存在系统逻辑不一致；
5. 测试结论缺乏测试记录、截图、日志或接口返回支撑；
6. 出现其他论文主题的模板残留；
7. 错别字、病句、口语化、不规范标点和中英文混排问题；
8. 参考文献格式和引用对应关系问题。

### 4. 保守修改

可以直接修改：

- 明显错别字、标点、语病；
- 技术名词规范，如 Spring Boot、Vue.js、RESTful API、MySQL；
- 可确定的标题层级和编号问题；
- 题目和正文能明确支撑的摘要表述；
- 明显模板残留且替换对象唯一明确的问题。

Word 修改稿中进行黄色突出显示时，必须尽量保留原有字符级格式，尤其是正文参考文献引用的上标、斜体、粗体、下划线、上下标、域代码和超链接样式。若修改范围包含或紧邻参考文献引用序号，应优先采用 run 级局部替换和局部高亮，保留原引用 run 的上标格式；不得为了高亮整句而把含上标引用的段落整体重写为单一 run。若当前工具无法可靠保留上标或复杂字符格式，应缩小修改范围、避开引用序号，或改为在修改说明中列出建议，不得输出会破坏引用上标格式的修改稿。

不得直接编造：

- 测试数据、测试截图、运行日志；
- 系统不存在或无法确认的功能；
- 数据库字段、源码行为、接口返回；
- 参考文献 DOI、页码、卷期、出版信息。

这些内容应列入“仍需人工确认的问题”。

## 四、输出文件要求

### Word 输入

输出 3 个文件：

```text
论文题目-修改稿.docx
论文题目-修改说明.md
论文题目-修改说明.pdf
```

### PDF 输入

输出 3 个文件：

```text
论文题目-修改稿.pdf
论文题目-修改说明.md
论文题目-修改说明.pdf
```

PDF 不再单独输出“逐项修改建议.md”或“可替换文本.md”。如需要替换文本，应合并写入“修改说明.md”和“修改说明.pdf”中的“具体修改情况”或“仍需人工确认的问题”。

## 五、PDF 批注规则

PDF 论文应优先采用“就近黄色批注”方式，效果接近人工在 PDF 页面上批注：

1. 对可定位的问题，尽量在问题文字下方或右侧附近添加黄色批注框；
2. 批注框距离问题位置不要太远，避免让读者来回寻找；
3. 批注框可以遮住附近不需要修改的普通文字，但不得遮住需要修改的原问题文字；
4. 批注框应使用清晰的黄色背景、橙色或深色边框，文字颜色清楚可读；
5. 批注内容应简短，包含“Revise 批注”或类似标识、问题说明和建议改法；
6. 如果工具支持箭头、短线或注释图标，可指向问题位置；
7. 如果无法精准定位，只能提取文本，则可在对应页附近添加页面级批注，并在修改说明中说明限制；
8. 不得声称已经完成原位文字替换，除非确实可靠替换了 PDF 正文。

PDF 修改稿必须保留原论文主体内容。若批注遮挡了部分无关文字，应在修改说明中说明这是批注式处理而非正文替换。

## 六、修改说明要求

修改说明必须包含：

1. 初评结果和评分表；
2. 主要问题概述；
3. 具体修改情况或建议替换表；
4. 摘要、关键词及英文翻译修改说明；
5. 图表与编号修改说明；
6. 参考文献核查与修改说明，并明确默认未核验 DOI；
7. Word 或 PDF 处理方式说明；
8. 仍需人工确认的问题；
9. 修改后复评或落实建议后的预计复评；
10. 总体评价；
11. 人工智能辅助生成说明。

默认使用简明中文撰写。

## 七、修改说明 PDF 排版要求

修改说明 PDF 必须以“可读、像正式文档”为目标，不能直接把 Markdown 管道表格当纯文本输出。

生成修改说明 PDF 时应遵守：

1. 页面使用 A4，页边距建议 18-22 mm；
2. 中文字体优先使用 Microsoft YaHei、SimSun、SimHei 或系统可用中文字体；
3. 标题字号建议 16-18 pt，一级小标题 12-14 pt；
4. 正文字号不小于 10 pt，建议 10.5 pt；
5. 表格字号不小于 9 pt，优先 9.5-10 pt；
6. 表格必须使用真实表格线，不得使用 Markdown 文本竖线模拟；
7. 表格线建议 0.5 pt 灰色或黑色，表头可用浅灰或浅黄色底色；
8. 单元格文字必须自动换行，垂直方向顶部对齐；
9. 表格内边距建议 4-6 pt，避免文字贴边；
10. 宽表不得强行压成极小字体，应拆分为多个窄表，或使用横向页面；
11. 多页表格应重复表头；
12. 表格不得明显溢出页面；
13. 初评表、具体修改表、复评表应保持清楚的网格线和一致的列宽；
14. 如果当前工具无法生成友好的表格 PDF，应优先生成 HTML 或 DOCX 中间稿再转 PDF，并在说明中如实写明。

## 八、命名与版本管理

安装目录和 frontmatter 名称使用 `revise`。  
对外显示名称使用 `Revise`。  
当前版本为 `3.0`。  
后续开源时建议通过 Git tag 管理版本，如 `v2.2`、`v3.0`，不要在 Skill 内部堆积冗长 changelog。
